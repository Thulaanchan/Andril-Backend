# Canonical M2 subscription entitlement dependency

Group limits read M2's existing `andril_economy.premium_entitlements` relation. The bridge resolves the creator's account from the private profile in the exact module. It observes the committed record under the PostgreSQL table lock used to coordinate with the canonical upsert, including the first insert. This lock also protects verified absence. An active Monthly or Annual record must have a supported finite expiry to qualify as Premium. Expiry and explicit Free or revoked state use the Free limits. Hidden, malformed or unavailable authority is denied.

The candidate M2 checkpoint `d51ba5924b95ed36d4bd01e571d7bdc2c52b27b1` remains on Member-2. Its InitialEconomy migration also installs wallet, payment and gift tables. Installing that migration here would import unrelated economy changes. The candidate service also treats the current auth subject as an internal account identifier, mutates expiry on read, and exposes grant/revoke contracts without a verified event or compare-and-swap revision. The candidate upsert can apply stale data while retaining the latest timestamp. The exact checkpoint has no GitHub workflow runs recorded.

The Groups code uses the compatible table and lock contract. Production activation requires a verified canonical M2 deployment with authenticated grant, renewal and revocation writers that reject stale transitions. No draft subscription writer, fallback relation, or issuance endpoint is enabled by this integration. The disposable Group fixture exercises grant, expiry, renewal and revocation through the canonical PostgreSQL relation.

## Canonical entitlement installation and transition authority

Install `scripts/database/install-canonical-entitlements.sql` with `psql -X -v ON_ERROR_STOP=1 -f scripts/database/install-canonical-entitlements.sql` after applying the Accounts migrations. The installation is transactional and intended to run once. It installs or adopts the isolated canonical M2 relation, validates supported subscription states, and adds the transition function and private event journal. Use the owning deployment identity for existing compatible canonical tables. The draft `InitialEconomy` migration originally targeted the same relation. See the synchronization notes below for its current scope.

Only separately approved server-side provisioning or a verified payment authority may receive `USAGE` on `andril_economy` and `EXECUTE` on `subscription_transition_revision(uuid)` and `apply_subscription_transition(uuid,uuid,timestamptz,integer,timestamptz,text,text)`. Use an individually identifiable service login for each authorized source. Keep the application and Group runtime principals and ordinary users out of that grant. Provisioners receive neither direct table access nor audit access. The deployment owner must remove any legacy direct writer grants before enabling the authority. There is no public grant operation or payment integration in this change.

The provisioning system checks the target and source evidence before invoking the function. It retains the event ID and the expected revision captured for the authorized decision. `NULL` represents verified absence. The function resolves the auth subject to the canonical account, writes and journals atomically, and rejects stale revisions. An exact repeat returns its original receipt without applying the change again. A rejected stale event requires a new authorized decision. A provisioner must not submit the same stale instruction paired with a newly read revision. Revoke operations persist a Free row so concurrent or replayed first-time grants cannot restore the previous entitlement. Group reads evaluate expiry without updating the subscription row.

## Member-2 synchronization

The reconciled Economy model can map the canonical relation for source compatibility. Its EF migrations manage wallet and gift tables and leave entitlement installation, transitions and rollback under the canonical SQL authority. On a fresh deployment, apply Accounts before running the canonical installer. Applying or rolling back Economy after installation preserves the entitlement table, audit journal and transition functions.

Member-2's draft Account and Economy implementations are preserved. The added Account and Economy HTTP actions, direct entitlement writer and test payment provider remain inactive pending their own runtime and security acceptance.
